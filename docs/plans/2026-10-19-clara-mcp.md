# Clara-ready MCP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Clara, docked beside Blockout, can stage, frame, light and export a shot using only Blockout's MCP tools. The same tools work from plain `claude`, `codex` and `copilot`.

**Architecture:** One tool catalog (`mcp/tools.json`) feeds two transports:
- the existing zero-dependency stdio bridge, and
- a new in-process Streamable HTTP server in the Electron main process.

Both relay each call through the existing control path (`control:invoke` IPC → `src/renderer/control/handler.ts`), so every edit stays undoable and visible live. A main-process controller attaches Clara through `@2dl/clara-client` from a titlebar button.

**Tech Stack:** Electron 43, electron-vite, TypeScript, Vitest, Playwright, `@modelcontextprotocol/sdk` ^1.30.0, zod ^4, `@2dl/clara-client` 0.1.0 (vendored tarball).

**Spec:** the Design section below. Lior skipped the design questions on 2026-10-19, so each decision is tagged *Lior* or *my call*. Background:
- the Clara brief, `D:\Git\maestro\docs\handoffs\apps\clara-mcp-handoff.md`
- the capability check, `.maestro/capabilities/` (local only)

## Design

**Why.** The fork exists to produce clean blockout clips for AI video-to-video models (see `CLAUDE.md`). Blockout's MCP can stage a shot but can't deliver one: it has no export, lighting, scenes, colours, mark editing, undo or save. `apply_camera_move` also ignores its `entityId`. Customers will drive Blockout by chatting with Clara, and Clara can only do what the tools allow.

**Decisions**
- *Lior:*
  - Code uses Blockout's upstream style (2-space indent, single quotes, no semicolons).
  - The fork stays mergeable with upstream: prefer new files and small hooks into upstream files.
  - Baseline he did not correct: almost nothing asks first, because store undo covers edits; deletes ask first; Clara gets `read-files` access and opens from a button.
- *Lior (DaVinci ruling D7, applied here):* Clara is always a separate install. Blockout never bundles it.
- *Lior (DaVinci ruling D1, applied here, my call to carry over):* Claude, Codex, Copilot and Clara all reach Blockout.
- *My call:*
  - **Transport:** in-process Streamable HTTP on `127.0.0.1:17480`. It gives plain-CLI users a stable URL, and it doesn't depend on a `node` binary on the customer's machine, which the stdio bridge needs.
  - The stdio bridge stays for upstream compatibility and reads the same catalog.
- *My call:*
  - **Server shape:** the low-level SDK `Server` with raw JSON schemas, so the catalog stays one JSON file that both transports read. `McpServer.registerTool` would need zod shapes.
  - **Relay:** tools wrap the existing renderer control actions; no new tool layer.
  - **CLI registration:** the HTTP server is registered with the CLIs, packaged builds only, as DaVinci does.
  - **Clara attach:** from a titlebar button, never at startup.
- *My call:*
  - **Clara's folder:** the open project's folder. With no project open, the button is disabled.
  - **Export default profile:** `seedance-2`. It is the only current video profile built around a reference video. Profiles for H3 Max, LTX Render-to-Real and Kling V3 Omni are a separate plan.
  - **Labelled entities** get distinct palette colours automatically, so the model can tell people apart.

**Goals**
- Fill the tool gaps:
  - export: shot, frame, contact sheet, scene animatic, plus a profile list
  - lighting
  - scenes and shots
  - an entity's look
  - camera rig
  - marks: list, edit, delete
  - motion per performer
  - undo, redo, save
  - richer `get_state`
- Every tool has a customer-facing `title`, a description, and `readOnlyHint` or `destructiveHint` where it applies.
- Camera moves and framing honour an explicit subject and never fall back to a set kit.
- Clara attaches, docks and detaches cleanly. Plain `claude` / `codex` / `copilot` reach the same tools.

**Non-goals:**
- new target-model profiles or prompt rewrites
- open roads
- camera occlusion
- fight and camera features (plan `2026-10-19-fight-camera.md`)
- bundling Clara

**Anti-goals:**
- a tool that can lose work without undo, unless it is marked destructive
- two catalogs drifting apart
- an MCP port reachable from another host or a browser page

## Global Constraints

- **Code style:** Blockout's upstream style in every file. 2-space indent, single quotes, no semicolons, and the existing JSDoc-style block comments. *(Lior, 2026-10-19)*
- **Mergeability:** prefer new files. Upstream files get small hooks only. Every task adds a line to `MODIFICATIONS.md`. Every modified upstream file keeps or gains the `// Modified … see MODIFICATIONS.md.` first-line header.
- **No commits:** stage only (`git add`). Lior reviews and commits. Never push. Never use worktrees.
- **AGENTS.md hard rules:**
  - `src/engine/` imports no DOM, three or Electron.
  - Nothing on the `state(t)` path uses unseeded randomness or time.
  - Every document change goes through `store.mutate(label, fn)` or an existing store action.
- **Done means:**
  - `npm run typecheck && npm run lint && npm test` all green; check Vitest's `Test Files` line.
  - Also `npm run smoke` when a task touches `src/main/`, `SceneManager.ts` or `export/`.
  - e2e specs run against the built app: `npm run build` first.
- **Launching Electron:** unset `ELECTRON_RUN_AS_NODE` first (Git Bash: `env -u ELECTRON_RUN_AS_NODE …`).
- **MCP HTTP server:**
  - Binds `127.0.0.1`. Default port `17480`; override with `BLOCKOUT_MCP_PORT`, an integer `0` or `1024..65535`.
  - Paths: `POST /mcp`, `GET /health`.
  - Returns 403 when the `Host` header isn't `127.0.0.1:<port>` or `localhost:<port>`, and 403 when any `Origin` header is present.
  - Sets `server.requestTimeout = 0`, because exports run up to 600 s.
- **Versions:** `@modelcontextprotocol/sdk` `^1.30.0`; `zod` `^4` (SDK peer `^3.25 || ^4`); `@2dl/clara-client` 0.1.0 (peer `electron >=35`).
- **Clara:**
  - Windows only (`'win32' === process.platform`); `appId: 'blockout'`; tool names snake_case.
  - Dev launch only behind `BLOCKOUT_CLARA_DEV` (the Maestro root) and only when `!app.isPackaged`. Never use `CLARA_DEV`.
- **Copy:** titles and descriptions are written for a non-technical customer. Error messages name the bad value and the tool that lists valid ones.

## Review Focus

### Task 6: In-process HTTP MCP server

**Files:**
- Create: `src/main/mcp-http.ts`
- Modify: `src/main/control.ts:37` (`startControlServer` returns `{ invoke }`)
- Modify: `src/main/index.ts:55-64` (start after the control server; stop on `before-quit`)
- Modify: `package.json` (dependencies)
- Modify: `mcp/README.md` (an "HTTP transport" section), `AGENTS.md` (the MCP tool table and the new tools)
- Test: `tests/unit/mcp-http.test.ts`, `tests/e2e/mcp-gaps.spec.ts`

**Interfaces:**
- Consumes: `mcp/tools.json` (Task 1), imported through `resolveJsonModule`.
- Produces in `src/main/mcp-http.ts`. It must not import `electron`; the tests run under Node.
  - `type InvokeFn = (action: string, params: unknown) => Promise<{ ok: boolean; data?: unknown; error?: string }>`
  - `interface McpToolDef { name: string; title: string; description: string; inputSchema: Record<string, unknown>; annotations?: { readOnlyHint?: boolean; destructiveHint?: boolean } }`
  - `interface McpHttpStatus { state: 'stopped' | 'listening' | 'error'; port?: number; url?: string; message?: string }`
  - `interface McpHttpServer { start(port: number): Promise<McpHttpStatus>; stop(): Promise<void>; status(): McpHttpStatus }`, where `start` never rejects
  - `createMcpHttpServer(opts: { invoke: InvokeFn; version: string; tools: McpToolDef[] }): McpHttpServer`
  - `toToolResult(response): CallToolResult`. A `data.imageBase64` string becomes one `image` content (`image/png`). Otherwise the result is one `text` content with `JSON.stringify(response)`, and `isError` is `response.ok === false`. This mirrors `blockout-mcp.mjs:550-560`.
  - `MCP_DEFAULT_PORT = 17480`, `resolveMcpPort(env: NodeJS.ProcessEnv): number`
- Produces in `src/main/control.ts`: `startControlServer(getWindow): Promise<{ invoke: InvokeFn }>`.

Per request:

Controller behaviour:
- On a platform other than `win32`: `unsupported`, and `toggle` is a no-op.
- From `idle`, `failed` or `not-installed`, `toggle(folder)` moves to `attaching`, then `attached` / `not-installed` / `failed`. An empty or null folder stays `idle` with the error `Open a project first`.
- `failed` gets one retry after `CLARA_RETRY_MS`; `not-installed` gets none.
- `toggle` while `attaching` bumps a generation counter. The handle that arrives late is `Detach()`ed, and the state goes to `idle`.
- `toggle` while `attached` calls `handle.Detach()` and moves to `idle`.
- `closed` from the current handle moves to `idle`; a stale handle is ignored.
- `mcpError` holds the MCP status `message` when the state is `error`.

## Open items carried from the Clara brief

- **Codex enforcement is weak.** It may skip Clara's approval card for `destructiveHint` tools, and its read-only sandbox can read outside `folder`. Deletes are safe anyway because of store undo; scans are removed from the scene but the file stays on disk.
- **Untested:** mixed-DPI docking, and the Clara setup run by a standard (non-admin) Windows user.
- **Attachments are images only.** Clara can't attach a reference video; `set_reference` takes a path.
- **Clara is unsigned,** so SmartScreen may warn on first run.
